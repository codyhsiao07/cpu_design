# 2026-09-06 主線檢查與修正報告

本次在 Windows 開發環境檢查 CPU／記憶體／MMIO 主線、FreeRTOS 與 Lua 移植層、host tools、
建置與驗證流程，並交叉檢查 Markdown 文件。從 commit
`04f65198bb95e820473640bac6690856ea968301` 的乾淨工作目錄開始；修改保留在工作目錄，沒有建立 commit。

使用 Python 3.13.1、Icarus Verilog 12.0 devel（`s20150603-1539-g2693dd32b`）、
xPack RISC-V GCC 15.2.0 與既有 FreeRTOS 202406.04-LTS kernel。

原有測試通過後，新增的負向與邊界測試仍找出下列問題。修正以最小行為變更為主，沒有搬動歷史 RTL、
改寫第三方 Lua／FreeRTOS kernel，或更換既有 bitstream。這是一次有明確範圍的檢查，不能視為所有指令、
交錯時序、遊戲規則或硬體環境的窮舉證明。

## 已修正問題與證據

| 編號 | 問題與影響 | 修正與回歸 |
|---|---|---|
| H1 | SYSTEM `funct3=100` 保留編碼被當作 ECALL／EBREAK／MRET，可能送出錯誤 exception cause 或改變控制流程 | `ID.v` 僅允許 `funct3=000` 進入三種 system instruction decode；unit TB 加入 `00004073`、`00104073`、`30204073`，並以真實 CPU 程式檢查三次 illegal trap |
| H2 | `mstatus.MPP` 可寫入未實作的 S／保留權限，`mret` 會進入這些狀態 | WARL 限制為 U／M，其他值映射 U；遍歷四種 MPP 編碼 |
| H3 | `mtvec` 讀回 MODE=1／3，實際卻一直以 direct mode 跳轉，軟體探測結果與行為不符 | 寫入及讀回 MODE 固定 0；保留 4-byte aligned base |
| H4 | CSRRS 讀取 `mip` 時把硬體 pending 複製進 `mip_sw`，外部 IRQ 消失後 pending 仍黏住；修改另一個 bit 也會污染 latch | read view 仍 OR 硬體訊號，但 RMW 基底改用 `mip_sw`；測試零 operand read 與同時修改 software bit |
| H5 | U-mode 且 MIE=0 時 machine interrupt 被永久遮蔽 | 有效 machine global enable 改為「目前低於 M-mode 或 MIE=1」；完整 CPU 程式證明 U-loop 可被 MSIP 中斷並返回 M-mode |
| H6 | software 與 timer 同時 pending 時，仲裁順序與 RISC-V machine interrupt 規則不同 | 改為 external > software > timer；加入兩種／三種來源同時 pending 測試 |
| H7 | VGA 控制暫存器只判斷任一 byte strobe；對控制位址高 byte 的 SB／SH 會意外清除 buffer selector | 僅在 `wstrb[0]` 寫入 selector；加入高 byte、零 strobe、framebuffer partial write 測試 |
| S1 | Lua 自製 `sqrtf` 在極小／大數嚴重失準；大 quotient 的 `fmodf` 回傳原值；非整數 `powf` 回傳 NaN；`frexpf(inf)` 不返回 | 改用工具鏈 RV32 soft-float `libm`；編譯參數仍是 RV32IM/Zicsr，不需要 F extension；Lua boot 加入極值、分數次方、餘數、infinity table key |
| S2 | 十進位文字逐位以 float 累加，使 `4294967296.0` 等字面值在執行前已失真；Lua `%` 的整合測試揭露此問題 | 使用 bounded significand 與 double 中間值，最後轉為 float；測試 2^32、長 mantissa／負 exponent 抵消、最小 subnormal、FLT_MAX 與不完整 exponent |
| S3 | 十六進位指數用 signed int 無限制累加；`0x1p4294967296` 會溢位，其他大指數可能卡在很長的 C 迴圈 | 飽和解析但消耗所有 exponent digits，使用 `ldexpf` 縮放；正負極大指數都做回歸 |
| S4 | Lua infinity 輸出先走數值轉整數流程而得到錯誤文字；負數在 size=1 buffer 未補 NUL | 明確輸出 `inf`／`-inf`，size=1 回傳空字串且不越界；使用帶 sentinel 的 C 測試 |
| V1 | 多 seed 腳本引用不存在的 `MIG_DDR3_interface.v` 並缺少當前依賴／top 選擇 | 從 repository 根目錄取主線 RTL，指定 `icache_pipeline_tb`／`FAST_SIM`，正常 elaboration 不使用 `-i` 隱藏缺失 |
| V2 | 模擬器 exit 7 但 log 含 PASS 時仍報成功；ERROR 與 PASS 同時出現也可能被接受；部分 RTOS／MulDiv wrapper 只看單一條件 | 同時要求 exit 0、預期 marker、無正式 failure marker；用 fake simulator 重現誤判並加入 host tests |
| V3 | 兩份空 trace、非法 register、超過 32-bit 的值會被接受；long verification 預設去除重複 commit，指定卻缺失的 reference 被 SKIP，舊 trace／coverage 可能被重用 | 嚴格輸入驗證；預設保留每筆 commit；缺失的必要 reference 判 FAIL；執行前清除該 case 的舊產物並要求新產物存在 |
| V4 | RV32M C smoke 只被編譯與檢查 mnemonic，真正執行時永遠回 FAIL：原 XOR golden `140AA3A0` 不正確 | 以獨立整數計算得到八個結果，逐一比較取代 XOR，避免錯誤互相抵消；CPU 執行回傳 `2800C0DE` |
| V5 | CPU TB 的 64-byte image path、128-byte trace path 會截掉長路徑開頭；父目錄 prefix 被 packed-vector concatenation 截除；MIG 指定缺失 image 時改載入預設程式 | 路徑容量統一為 1024 bytes，使用 `$sformat` 組合路徑，明確指定的缺失 image 直接報錯；新增三個 Icarus 整合測試 |

H2／H3／H5／H6 參照 [RISC-V Machine-Level ISA](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)
的 WARL、trap-vector 與 interrupt 規則。專案仍是精簡 CSR 平台，以上修正不等同完整 privileged ISA 相容性認證。

V4 的獨立計算結果（依程式呼叫順序）為：

```text
MUL     AF37B5F8
MULH    00000136
MULHSU  FFFFFFFF
MULHU   121FA00A
DIV     FFFA21A8
DIVU    000E0042
REM     FFFFFF43
REMU    00000930
XOR     42DC3CA2
```

此外，large boot CRC TB 現在可指定 image path、length、CRC；runner 使用 host `zlib.crc32`
計算輸入參數，避免韌體更新後仍使用舊 CRC。缺失／含 unknown word 的 image 會明確失敗。

## 重現方式

在 repository 根目錄執行，必要時覆寫工具名稱／路徑：

```powershell
python -m unittest discover -s tools -p "test_*.py" -v
python tools/run_regression.py --seed-count 5 `
  --gcc C:/riscv/xpack-riscv-none-elf-gcc/bin/riscv64-unknown-elf-gcc.exe `
  --objcopy C:/riscv/xpack-riscv-none-elf-gcc/bin/riscv-none-elf-objcopy.exe

powershell -NoProfile -ExecutionPolicy Bypass -File tools/gen_ref_traces.ps1 `
  -OutDir build_ref_traces -AllowMiss 0
powershell -NoProfile -ExecutionPolicy Bypass -File tools/run_long_verification.ps1 `
  -Tests 24,25,26,27 -SeedCount 1 -OutDir build_long_verification `
  -SimExe build_long_verification/cpu.out -RefTraceDir build_ref_traces

powershell -NoProfile -ExecutionPolicy Bypass -File tools/run_rtos_lua_sim.ps1 `
  -BuildDir build_rtos_lua_sim
python tools/run_regression.py --suite unit --boot-image build_rtos_lua_sim/rtos_lua.mem
```

其餘 RTOS profiles 使用對應的 `run_rtos_smoke/preflight/console/platform_sim.ps1`。
外部 FreeRTOS kernel 位置與工具鏈覆寫方法見 [REQUIREMENTS.md](../03-build-boot/REQUIREMENTS.md)。
新 runner 在任何 working directory 都能找到 RTL；相對 `--out-dir`／`--boot-image` 則以呼叫目錄為準。

## 架構評估與後續加強順序

1. **把本次回歸固定成 CI 門檻。** 每次 RTL 變更跑 unit＋directed，定期跑更多 random seeds；
   用同一套 marker／exit-code 規則產生機器可讀結果。新 runner 已提供此入口，CI 服務本身未設定。
2. **擴大獨立 architectural reference。** 現有 Python ISS 只覆蓋 RV32I/GPR write sequence；
   接下來應比較 PC、instruction、store、CSR 與 exception side effects，並補 M extension／interrupt reference。
   現在的 52,235 筆一致不能偵測所有同值重複、遺漏 store 或 trap ordering 問題。
3. **整理 top-level 邊界。** `icache_pipeline_top.v` 同時負責 pipeline、MMIO、trap control、MIG 選擇與 perf bank；
   後續可逐步抽出 MMIO decode／register bank，統一 address constants，再以目前測試保護重構。
4. **讓 firmware build 與模擬使用同一份 profile metadata。** 避免 clock、memory size、PASS marker、
   toolchain path 在多個 PowerShell script 分散維護。裸機 Makefile 的 header／flag 依賴追蹤也應優先補強，
   更改組態時目前仍應使用新的 BUILD_DIR 或乾淨建置。
5. **補 host-native Lua 數值／protocol fuzz。** 本次已增加 CPU 上的數值與 Lua boot 回歸；仍應針對任意長度字串、
   halfway rounding、NaN、subnormal、stop/timeout 與 UART 混合輸入建立更大測試集。
   當前 decimal parser 使用 18 位有效數字，沒有宣稱所有十進位輸入都 correctly rounded。
6. **保留明確的主線與歷史來源分類。** 正式回歸只涵蓋根目錄主線 RTL；`cache_old/`、`temp/`、
   `storage_top/`、`replaced_and_store_file/` 尚未轉為受維護的產品組態。未刪除這些參考資料。
